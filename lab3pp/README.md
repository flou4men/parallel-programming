## Схема распараллеливания

Реализовано классическое блочное распределение по строкам: матрица `A` (и результирующая `C`)
делится на непрерывные полосы строк, по одной полосе на процесс; матрица `B` нужна всем процессам
целиком, поэтому один раз рассылается широковещательно.

```
rank 0: читает A.txt, B.txt
        │  MPI_Scatterv (A раздаётся полосами строк)
        │  MPI_Bcast    (B целиком — всем процессам)
        ▼
каждый процесс: C_local = A_local × B   (те же циклы i–k–j, что в л/р №1)
        │  MPI_Gatherv  (полосы результата собираются на rank 0)
        ▼
rank 0: записывает result.txt, печатает метрики
```

Ключевые фрагменты:

```cpp
// блочное распределение строк: rank r получает counts[r] элементов по смещению displs[r]
const int baseRows = n / procs, extra = n % procs;
for (int r = 0; r < procs; ++r) {
    const int rows = baseRows + (r < extra ? 1 : 0);
    counts[r] = rows * n;
    displs[r] = (baseRows * r + std::min(r, extra)) * n;
}

MPI_Scatterv(rank == 0 ? a.data() : nullptr, counts.data(), displs.data(), MPI_DOUBLE,
             localA.data(), localElements, MPI_DOUBLE, 0, MPI_COMM_WORLD);
MPI_Bcast(broadcastB.data(), n * n, MPI_DOUBLE, 0, MPI_COMM_WORLD);

// локальное умножение своей полосы — тот же порядок циклов i–k–j, что в л/р №1
for (int i = 0; i < localRows; ++i) {
    double* c = &localC[static_cast<size_t>(i) * n];
    const double* aRow = &localA[static_cast<size_t>(i) * n];
    for (int k = 0; k < n; ++k) {
        const double number = aRow[k];
        const double* bRow = &broadcastB[static_cast<size_t>(k) * n];
        for (int j = 0; j < n; ++j) c[j] += number * bRow[j];
    }
}

MPI_Gatherv(localC.data(), localElements, MPI_DOUBLE, rank == 0 ? result.data() : nullptr,
            counts.data(), displs.data(), MPI_DOUBLE, 0, MPI_COMM_WORLD);
```

Как и в л/р №1, для элемента `C[i][j]` считается сумма произведений `A[i][k] · B[k][j]`, сложность
≈ 2N³ операций. Строки `A` делятся без наложений, гонок данных нет: обмен между этапами выполняют
коллективные операции MPI, которые сами синхронизируют процессы.

Программа печатает одной строкой:

```
N=2000 procs=16 nodes=2 ... time_sec=... time_min_sec=... compute_sec=... comm_sec=... gflops=... hosts="n1,n2" verify=PASS max_diff=0.000e+00
```

где `time_min_sec` — минимум полного времени цикла «рассылка → счёт → сбор», `compute_sec` — время
локального умножения, `comm_sec` — время обменов, `nodes`/`hosts` — узлы кластера, на которых
реально работали процессы.

`lab3.pbs` сам загружает Intel MPI, компилирует программу и запускает серию:

```bash

export I_MPI_DEVICE=rdma
```

Скрипт `run_experiments.sh` не требует Python на узлах: матрицы генерирует сама MPI-программа
(`--generate N`), а все замеры складываются в `results.txt`. Для каждой точки выполняется

```bash
mpirun -r ssh -machinefile $PBS_NODEFILE -np <p> ./matrix_mpi --repeats 3 --warmup 1
```

Строка `-r ssh -machinefile $PBS_NODEFILE` — рекомендованная в документации кластера форма запуска
Intel MPI внутри задания PBS. После завершения задания в каталоге появятся `lab3_matrix_mpi.o<номер>`
(полный вывод задания) и `results.txt` с протоколом замеров.

В протокол попадают строки вида

```

```

Протокол переносится на ноутбук (WinSCP), после чего таблицы, графики и раздел результатов отчёта

## Методика эксперимента

- Размеры матриц: **200, 400, 800, 1200, 1600, 2000**.
- Число процессов: **1, 2, 4, 8, 16, 32** (1–8 — один узел, 16 — два, 32 — четыре узла по 8 ядер).
- В каждой точке: 1 прогрев + 3 замера, в таблицах — минимум (среднее хранится в `benchmark.csv`).
- Замеряется полный цикл работы программы (`MPI_Wtime`), отдельно измеряются время счёта и время
  обменов (`Scatterv` + `Bcast` + `Gatherv`).
- Матрицы для всех значений `p` одинаковые: их создаёт сама программа (`--generate N`, фиксированный
  seed 42, целые значения от −5 до 5 — как в генераторе л/р №1).
- После каждой точки результат проверяется двумя способами: независимым расчётом `A @ B` в NumPy
  (`check.py`, если NumPy есть на кластере) и встроенной сверкой `--verify` (последовательный эталон
  на rank 0, выполняется для `p = 4` в каждой серии).
- Имена узлов и их число выводятся в метриках и сохраняются в `results.txt` — это подтверждение
  того, что задача действительно выполнялась на вычислительных узлах кластера.

## Проверка корректности

Результат каждой точки проверяется двумя независимыми способами:

1. `check.py` — перемножение `A @ B` в NumPy и сравнение поэлементно (`np.allclose`,
   rtol = 1e-9, atol = 1e-7) с записанным `result.txt`.
2. встроенная сверка `--verify` — на rank 0 после сбора результата считается последовательный
   эталон и сравнивается с распределённым; в выводе печатается `verify=PASS max_diff=…`.

Обе проверки выполняются на кластере, их результаты сохраняются в `results.txt`.

## Контрольные вопросы (кратко)

**Что такое MPI и чем он отличается от OpenMP?** MPI — стандарт обмена сообщениями для систем с
распределённой памятью: процессы имеют собственные адресные пространства и общаются явными
операциями (точка-точка, коллективные). OpenMP работает внутри одного процесса с общей памятью.

**Что такое коммуникатор и ранг?** Коммуникатор — группа процессов с общим контекстом обмена
(`MPI_COMM_WORLD` — все процессы); ранг — номер процесса в коммуникаторе (0…size−1).

**Чем коллективные операции отличаются от точка-точка?** Коллективные (`Bcast`, `Scatterv`,
`Gatherv`, `Allreduce`) выполняются всеми процессами группы одновременно и обычно лучше
оптимизированы под топологию сети; точка-точка (`Send`/`Recv`) — обмен между двумя процессами.

**Зачем в этой работе `Scatterv` и `Gatherv`, а не `Scatter`/`Gather`?** Размер матрицы `N` может не
делиться на число процессов, поэтому нужны операции с массивами счётчиков и смещений (переменный
размер блока).

**Почему матрица B рассылается всем процессам?** Каждой полосе строк `A` нужна вся матрица `B`, поэтому
`B` либо рассылается (`MPI_Bcast`, как здесь), либо умножается блоками с обменом между соседями —
второй вариант сложнее, но уменьшает объём передач.

**Почему ускорение меньше числа процессов?** Накладные расходы на обмены (в `Bcast` участвует вся
матрица `N²` элементов), закон Амдала, неравномерность загрузки при `N`, не кратном `p`, и рост
времени передачи с числом узлов.

**Как уменьшить объём обменов?** Блочное (2D) умножение: матрицы делятся на плитки, каждый процесс
хранит по полосе `A` и полосе `B` и пересылает только плитки соседям — объём передач растёт как
`N²/√p` вместо `N²`.
